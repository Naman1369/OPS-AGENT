Final year project · Plain-English walkthrough

OPS-AGENT

An AI system that reads IT support tickets, looks up the company's own troubleshooting documents, drafts a fix — and then, crucially, decides for itself whether that fix is safe to send or needs a human first.

D. Y. Patil College of Engineering & Technology CSE (AI & ML), 2026–27 Written for readers with no technical background
01

The problem, in one paragraph

Every company has an IT helpdesk. When your laptop dies, your password stops working, or the office Wi-Fi drops, you file a “ticket” and a support engineer eventually works through it. Large companies get thousands of these a week, and most are things the engineers have solved a hundred times before. It is slow, repetitive, and expensive.

The obvious modern fix is to point an AI chatbot at the pile. Plenty of companies have. The problem is what happens when the AI is wrong but sounds confident — it tells someone to delete the wrong folder, or quietly handles what was actually a security breach. Chatbots are good at sounding certain. They are bad at knowing when they should not be.

OPS-AGENT's argument is that the interesting problem isn't answering the ticket. It's knowing when not to answer it.

02

The idea: four specialists, not one generalist

Instead of one AI trying to do everything, OPS-AGENT splits the job across four smaller programs called agents. Each does one thing and hands its work to the next, like a relay team. Think of an assembly line in a repair shop rather than a single mechanic.

The fourth one is the unusual part, and it's the whole point of the project.

The four agents
AgentWhat it doesEveryday analogy
Intake Reads the raw complaint and sorts it: what kind of problem is this, how urgent, what are the key words to search on? The receptionist who takes your details
Retrieval Searches the company's own troubleshooting manuals for pages that match the problem. The librarian who fetches the right manual
Resolution Reads those pages and writes step-by-step instructions — using only what the pages say. The engineer who writes the fix
Governance Checks the answer against seven safety rules and decides: send it, or hand this to a human? The supervisor who signs off

How a ticket moves through the system

A ticket enters on the left and leaves on the right — either as an answer sent straight to the user, or as an escalation to a human engineer. The two dark arrows are the safety rules that are built into the shape of the system rather than merely written down as instructions.

04

Following one real ticket

Here is an actual run of the finished system. The ticket is a common one: someone's work VPN — the secure connection that lets you use office systems from home — won't connect, and shows an error numbered 809.

  1. 1

    The ticket arrives

    Just a sentence of ordinary English, exactly as a frustrated employee would type it.

    "User cannot connect to the VPN, error code 809"
  2. 2

    Intake sorts it

    The first agent pulls structure out of that sentence. It spots that this is a network problem, that it isn't an emergency, and — importantly — it catches the error number, which is the single most useful thing to search on.

    category network priority P3 (P1 = whole office down, P4 = no rush) error code 809 keywords vpn, cannot connect, 809, error, code
  3. 3

    Retrieval finds the manual

    The second agent searches a library of 30 troubleshooting articles. It doesn't match words literally — it matches meaning, so a ticket saying “can't get on the VPN” still finds the article titled “VPN Connection Fails”. Each result gets a relevance score out of 1.

    1. [0.36] KB-0001 VPN Connection Fails with Error 809 2. [0.22] KB-0002 VPN Client Repeatedly Prompts for Credentials 3. [0.16] KB-0004 Internal Sites Unreachable (DNS Failure)

    Anything scoring too low is thrown away rather than passed on. A weak match is worse than no match, because it gives the next agent something plausible-looking to build a wrong answer on.

  4. 4

    Resolution writes the fix

    The third agent turns the retrieved article into numbered instructions. Every single step ends with a tag in brackets naming the document it came from — so an engineer can always check the source. It also reports how confident it is.

    1. Confirm the user is not on a captive-portal network that blocks UDP 500 and UDP 4500. [KB-0001] 2. Enable NAT traversal: set the registry value AssumeUDPEncapsulationContextOnSendRule to 2. [KB-0001] 3. Reboot the workstation. [KB-0001] ... 3 more steps confidence 0.49
  5. 5

    Governance decides

    The fourth agent runs its seven checks. Six pass. One doesn't: the confidence of 0.49 is below the required 0.70. So the answer is not sent automatically.

    (ok ) G1 grounded evidence was found (ok ) G2 cited sources are real (blocked) G3 confident 0.49 is below 0.70 (ok ) G4 complete steps exist (ok ) G5 priority gate not a P1 (ok ) G6 category gate not security (ok ) G7 intake clarity ticket was understood verdict ESCALATE TO HUMAN

    The engineer doesn't get a bare “couldn't handle it.” They get the draft answer, the sources, and the exact reason it was held back — a head start rather than a dead end.

05

The seven checks

These are the safety rules. All seven must pass for an answer to go out on its own. Any single failure sends the ticket to a person.

Governance policy v1
CheckNameWhat it asks
G1GroundedDid we actually find a supporting document, or are we guessing?
G2CitedDoes every source the answer names really exist? (An AI citing a document that was never retrieved has invented it.)
G3ConfidentIs the confidence score above the threshold?
G4CompleteIs there an actual answer with actual steps, not an empty shell?
G5Priority gateIs this a P1 emergency? Those always go to a human, however confident the AI is.
G6Category gateIs this a security incident or lost data? Those always go to a human too.
G7Intake clarityDid we understand the ticket well enough to be answering it at all?

G5 and G6 are deliberately blunt. If someone reports a suspected phishing email, it goes to a human even if the AI is 99% sure it knows the answer — because being wrong about a security breach costs far more than an unnecessary escalation.

06

The bit that makes this a research project

Here is the insight the whole project rests on, and it's worth understanding even if you skip everything else.

When an AI says it is “90% confident”, that number is not trustworthy. Researchers have measured this repeatedly: AI models are systematically overconfident. They are most convincing precisely when they're inventing things.

Now, most AI systems that try to add a safety layer add it as another AI — a second model asked “is this answer good?” But that second model has exactly the same weakness as the first. You've asked an unreliable judge to review an unreliable witness.

So OPS-AGENT's Governance agent contains no AI at all. It is seven fixed rules, written in ordinary code — the kind of thing a pocket calculator does. Same input, same answer, every time, with the reason written down.

That's what “deterministic governance” means in the project's title, and it buys three things a company actually needs: the decision can be audited (you can show a regulator exactly why a ticket was escalated), it can be reproduced (run it again, get the same result), and it can be explained (no shrugging and saying “the model decided”).

The measurement that comes next

The confidence score the system currently uses is the AI's own raw, untrusted number. The next phase of the project takes a set of tickets with known answers, measures how wrong that number is, and mathematically corrects it — so “70% confident” genuinely means right about 70% of the time. The project will then measure whether that correction reduces failures compared to three simpler systems. That comparison is the actual research result.

What “finished and tested” means concretely: 92 automated tests pass, and a separate verification script walks a ticket through all four agents step by step and confirms all 49 of its checks — including that no information is lost between agents, and that a nonsense ticket never reaches the answer-writing step.

Running it yourself

It works with no API key and no internet connection, using a built-in offline mode — useful for demos.

# one-time setup
py -3.10 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

# build the searchable article library
python scripts/ingest_kb.py

# watch a ticket travel through all four agents
python scripts/verify_pipeline.py

# run the test suite
pytest

The last command is the quickest way to see that it works: 92 tests, about a second and a half.

09

Jargon, translated

Terms that come up in the code and the report, in plain language.

Agent
A program given one job and the ability to decide how to do it. Four of them here.
LLM
Large Language Model — the technology behind ChatGPT. It predicts text, which is why it can write a fix but also why it can confidently write a wrong one.
Hallucination
When an AI states something false as if it were fact. The single biggest risk this project is designed around.
Grounding
Forcing the AI to answer only from documents you gave it, rather than from memory. The main defence against hallucination.
RAG
Retrieval-Augmented Generation — the formal name for “look it up first, then answer.” Steps 3 and 4 of the walkthrough.
Vector database
A search index that finds documents by meaning rather than by exact words, so “can't get online” can match an article about network failures.
Embedding
The trick that makes the above work: text is converted into a list of numbers, and texts with similar meanings end up with similar numbers.
LangGraph
The framework used to wire the four agents together and control which one runs next.
Confidence score
The AI's own 0-to-1 estimate that its answer is right. Currently untrusted — correcting it is the next phase.
Calibration
Mathematically correcting that score so it means what it says.
Escalation
Handing a ticket to a human instead of answering automatically.
Deterministic
Same input always produces the same output. True of the Governance agent, deliberately not true of AI models.
Audit trail
A permanent record of every decision and why it was made — what a company would show a regulator.
P1 / P2 / P3 / P4
Standard helpdesk urgency levels. P1 is “the whole office has stopped working”; P4 is “whenever you get a chance.”
MAST
A published catalogue of the 14 ways multi-agent AI systems typically fail. The project will use it to count and classify its own failures.
